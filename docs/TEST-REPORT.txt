Hollyhock Custom Launcher 0.6.1 - validation report
Validation date: 2026-11-09

Targets
-------
HH2: installed Hollyhock 2 on OS 02.01.2000.0000, HHK, HH3 and compatible native BIN.
HH3: installed Hollyhock 3 on OS 02.01.7002.0001, HH3 ELF.
Both use the pinned SDK and GCC 15.2.0 SH toolchain; separate object/output dirs.

Host checks
-----------
Both variants run the real UI controller/renderer, actual GUI adapter, discovery,
MCS history, launch orchestration and OS-return tests. Sanitizers remain enabled.
Fixtures cover 1000 apps, mixed touch/key events, 25000 UI transitions, five-entry
history, malformed MCS records, write-free browsing/closing and non-fatal errors.
HH3 metadata tests retain buffered reading and cached getters.
Variant history uses distinct variables/signatures while preserving HH3 records.

ClassPad design update
---------------------
Both variants use the same ClassPad-style frame, cyan press/selection feedback,
wider Run/Close buttons and separated app details. Closed, open, recent, empty
and pressed states are rendered from the real controller/renderer as previews.
Each variant passes 23 UI checks and 7 SDK-adapter checks, including redraws when
a row press turns into a drag or is cancelled horizontally. Startup still reads
details for only the selected app; revisiting an app reuses the cached details.
Idle events do not redraw. Description text is rendered without a combined copy.

HH2 checks
----------
Native big-endian SuperH ELF section validation, including symbol-stripped files,
metadata, entry point, PROGBITS/BSS, RAM boundaries and overlaps.
Native BIN default/header addresses, optional metadata and invalid destinations.
Malformed headers, overflowed offsets, wrong CPUs/endian, and 200 structural
mutations are checked. Actual loader copy/BSS operations use mapped app RAM.
Invalid files leave that RAM untouched; unloaded apps cannot execute.
The fixed-address loader probe uses UBSan because ASan shadow overlaps the mapped
address. Pure parser checks use ASan plus UBSan.

Target checks
-------------
Actual SH ELF architecture, entry, image bounds, OS guard and required SDK
symbols are checked for both variants. MCS enum/byte representation is verified
from target compiler output. Real HH2 test HHK/BIN load addresses and allocated
section bytes are cross-checked.
HH3 additionally runs the narrow instruction consumer against the compiled
return object/callback and the null-return regression.
HH2 retains the upstream native OS completion-dialog return path.

Packaging
---------
Packages require passing host/target reports for the same variant and input
hash, and the target report must match the run.bin hash. ZIP CRC, source
inventory, both OS address files, SDK/license inclusion and inner/outer SHA256
lists are checked. Release jobs wait for both variants.

Evidence and limits
-------------------
Actual per-build commands and outputs: tests-host.json and tests-target.json.
Dynamic hashes, compiler and source revision: BUILD.json.
SDK/OS calls are mocked in host tests. No physical calculator execution, firmware
patching or full OS emulation was performed. Persistent MCS storage, OS dialog
behavior and real startup/load timings still require hardware validation.
Earlier HH3 metadata operation counts remain documented in PERFORMANCE.md;
they are not calculator timing measurements and do not describe the HH2 format.

0.6.1 format-search regression
-----------------------------
One full directory scan; original case-sensitive OS filenames are returned
unmodified by the mock. Mixed HHK/HH3/BIN cases, exact loader dispatch, own
launcher exclusion, 1000 apps, malformed names and find-handle error paths.
HH2 history covers all three formats. Both builds run ELF metadata/load tests.
The real ELF loader is tested against mapped RAM for segment copies, BSS,
preflight failures and entry-call arguments/environment. A host trampoline
checks the calling convention, not SH instruction execution. The unchanged
SDK resolver is exercised with a mapped ROM guard and selected OS addresses;
these host records use host pointer width. Target checks independently verify
the actual embedded SH-width symbol table and the shared HH3 SDK test app.
